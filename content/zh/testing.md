这里的大多数驱动从未接触过它们的设备。本页介绍在没有硬件的情况下检查它们的唯一方法——以及这种检查的边界在哪里。

## 问题所在

libsigrok 有 87 个驱动，对应的硬件我们谁都没有。仅仅从 C 源码移植会得到一份能编译、却从未与任何设备通信过的代码。录制数据是常见的替代方案，但它们同样需要这些设备。

## 思路

一个用 Rust 编写的设备模型，通过 Linux 的 `vhci-hcd` 以 USB/IP 方式挂载，让内核看到的是一个真实的 USB 设备。真实的 `sigrok-cli` 和 `oxrok` 不加修改地对同一设备运行，每一次传输都被记录下来。然后进行对比。

## 比较什么

输出、错误、退出状态、每一次 USB 传输，再加上对 C 驱动的 gcov 覆盖，以查看触达了哪些代码。总线上逐字节一致，比输出一致是更强的断言。它并非无条件成立：节点编号和设备地址会被泛化处理，一个用例也可以出于明确原因过滤掉某些差异。

## 模型是敌对的

模型不会接受任何到达的东西。它会标记发送到配置中不存在的端点的传输、其协议所禁止的内容，并按需表现出异常行为：STALL 请求、过短或垃圾应答、永不完成的传输、在选定的传输处拔插。错误路径正是 C 实现与移植版差异最大的地方。

## 它无法告诉你的

模型是根据 C 驱动和任何可获得的公开资料构建的，因此它可能共享 C 对设备的误解。匹配它只能证明在用例触达的路径上与 libsigrok 一致，而非在硬件上的行为正确。时序并不真实：模型计算的是主机的传输次数而非时钟，而且 USB/IP 没有总线。因此真实证据优先于它：录制数据、手册、历史。C 隐式依赖、却未言明的怪癖无法用这种方式发现。
